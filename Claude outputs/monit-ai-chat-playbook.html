01

ภาพรวมระบบที่อ่านมา

agent bash บนแต่ละโฮสต์ยิง JSON ทุก 10 วินาที → ingest API → system_metrics (hypertable) → continuous aggregate metrics_1m / metrics_1h → alert engine (state machine debounce/hysteresis/flapping) → pg-boss → Telegram/Slack/Webhook → dashboard Vue 3

สิ่งที่สำคัญที่สุดสำหรับงานนี้คือ ข้อมูลที่คุณมีอยู่แล้วเยอะกว่าที่ AI เห็นมาก agent เก็บมาครบทั้ง cpu ต่อคอร์, ram, load, disk ต่อ mount, network counter, gpu, docker, pm2, http health check, mysql/postgres connection และที่น่าสนใจที่สุดคือ topology ของ MySQL NDB Cluster

ตัว collector collect_ndb() ดึงจาก ndbinfo.config_nodes / ndbinfo.nodes / ndbinfo.membership / ndbinfo.memoryusage และเสริมด้วย ndb_mgm -e show แล้วรวมเป็น array ที่มี node id, type (NDB/MGM/API), host, status, nodegroup พร้อม arbitrator และ data/index memory — นี่คือทุกอย่างที่ต้องใช้วาดแผนผังคลัสเตอร์จริง โดยไม่ต้องเดาเลยสักช่อง

ข้อสรุปสำคัญ — ปัญหาไม่ใช่ "โมเดลโง่" แต่เป็น "เราให้ข้อมูลโมเดลน้อยเกินไป และปิดโหมดคิดของมันทิ้ง" ตัวเลขทุกตัวที่ต้องใช้วิเคราะห์อยู่ในฐานข้อมูลอยู่แล้ว แค่ยังไม่เคยเดินทางไปถึง prompt

layer 1Grounding — ให้ข้อมูลที่ถูกต้องและคิดมาแล้ว
T1

Deterministic Analytics Pre-computation (Context Pack)

~1 วันผลสูงสุดต่อแรง

หลักการเดียวที่สำคัญที่สุด: อย่าให้ LLM ทำเลขคณิต ให้ Postgres ทำ โมเดล 27B ที่รันเองมักคำนวณ p95 หรือหาความชันจากตัวเลขดิบพลาด แต่ตีความข้อสรุปเชิงตัวเลขได้ดีมาก เพราะฉะนั้นให้ SQL คำนวณเสร็จก่อน แล้วส่ง "ข้อสรุป" ไปให้มันอ่าน

สิ่งที่คำนวณล่วงหน้าต่อ server:

  • ค่าปัจจุบัน + p50 / p95 / max ของ cpu, ram, disk, load ในหน้าต่าง 1h / 24h / 7d จาก metrics_1m และ metrics_1h
  • trend slope ด้วย regr_slope() ที่ Postgres มีอยู่แล้ว ไม่ต้องลงไลบรารีเพิ่ม
  • disk-full ETA — จาก slope ของ disk_avail_kb → เหลืออีกกี่วันเต็ม
  • anomaly score — z-score / MAD เทียบ "ชั่วโมงเดียวกันของ 7 วันก่อน" ไม่ใช่เทียบค่าเฉลี่ยรวม เพื่อไม่ให้ daily seasonality หลอก
  • load per core (load_1m / cores) — ตัวเลขที่แปลผลได้จริงว่าเครื่องอิ่มหรือยัง
  • network rate จากผลต่าง counter — โค้ดคุณมี gap guard อยู่แล้ว เอามาใช้ซ้ำได้เลย
-- ตัวอย่าง: slope + ETA ดิสก์เต็ม (Postgres ล้วน ไม่ต้องมี extension เพิ่ม)
WITH d AS (
  SELECT server_id,
         extract(epoch FROM bucket) AS t,
         disk_avail_kb              AS y
  FROM   metrics_1h
  WHERE  bucket > now() - interval '14 days'
)
SELECT server_id,
       regr_slope(y, t)                       AS kb_per_sec,
       min(y)                                 AS avail_kb_now,
       CASE WHEN regr_slope(y, t) < 0
            THEN (min(y) / -regr_slope(y, t)) / 86400.0
       END                                    AS days_to_full
FROM   d GROUP BY server_id
HAVING regr_slope(y, t) < 0
ORDER  BY days_to_full;

ผลลัพธ์ที่ส่งเข้า prompt: web-01 · ram 84.2% (24h p95 91.0, 7d +1.8%/d) · disk / 91% avail 8.2GB ETA 6.4d ⚠ · load 7.9/8 cores

บรรทัดเดียวแบบนี้ทำให้โมเดลพูดเรื่อง "แนวโน้ม" กับ "ความผิดปกติ" ได้ทันที โดยไม่ต้องแตะ vLLM เลยสักบรรทัด

T2

System Prompt เชิงบทบาท + Analysis Protocol

ครึ่งวันผลสูง

เปลี่ยนจาก "ผู้ช่วยตอบคำถาม" เป็น "SRE ที่กำลังสอบสวน fleet" แล้วใส่สี่อย่างที่ prompt ปัจจุบันไม่มี

  • ความรู้เฉพาะระบบนี้ ที่โมเดลไม่มีทางรู้เอง เช่น disk.used_pct คือพาร์ทิชันที่แน่นที่สุด ส่วน disk.total_used_pct คือทั้งเครื่องรวมกัน — comment ในไฟล์ metrics.js ของคุณอธิบายไว้ดีมากอยู่แล้ว ยกไปใส่ prompt ได้เลย เช่นเดียวกับกฎ NDB ว่า node group ที่ node ตายหมดกลุ่ม = คลัสเตอร์หยุดรับเขียน
  • Analysis protocol บังคับลำดับคิด: สังเกต → หา correlation ข้าม server และข้ามเวลา → ตั้งสมมติฐาน → อ้างหลักฐานเป็นตัวเลข → เสนอคำสั่งที่รันได้จริง → บอกระดับความมั่นใจ
  • กฎ grounding: ทุกข้อสรุปต้องอ้างตัวเลขที่มีใน context ถ้าไม่มีให้เรียก tool ถ้ายังไม่มีให้บอกว่าไม่มีข้อมูล ห้ามเดา — และห้ามแปลง "ไม่มีข้อมูล" เป็น "ปกติดี"
  • few-shot สองตัวอย่าง: คำถามค้นหา (ตอบสั้น 1–2 บรรทัด) กับคำถามวิเคราะห์ (ตอบตาม protocol) — สอนรูปแบบด้วยตัวอย่างได้ผลกว่าคำสั่งยาวเป็นย่อหน้ามาก โดยเฉพาะกับโมเดลขนาดนี้
T3

คุมโหมดคิดและ sampling แยกตามชนิดคำถาม

2 ชม.ผลสูง

เอา /no_think ออกจาก prompt แล้วย้ายไปคุมที่ API แทน จะได้เลือกได้ต่อคำถาม

// lookup — เร็ว แม่น ไม่ต้องคิดยาว
{ temperature: 0.2, top_p: 0.8,  top_k: 20, max_tokens: 512,
  chat_template_kwargs: { enable_thinking: false } }

// analysis / report — เปิดโหมดคิด ใช้ค่าที่ Qwen3 แนะนำ
{ temperature: 0.6, top_p: 0.95, top_k: 20, max_tokens: 4096,
  presence_penalty: 1.0,                      // กัน loop ของ local quantized model
  chat_template_kwargs: { enable_thinking: true } }

ฝั่ง ChatView.vue ตอนนี้ตัด <think>…</think> ทิ้ง — เปลี่ยนเป็นเก็บไว้ในบล็อกพับได้ "ดูวิธีคิด" จะตรวจสอบเหตุผลได้ และเป็นหลักฐานเวลามันตอบผิด

ต้องเช็คก่อน — --max-model-len ที่ serve อยู่เท่าไร ถ้าจะทำ report ต้องมีอย่างน้อย 32k และควรเปิด --enable-prefix-caching เพราะ system prompt จะยาวขึ้นแต่คงที่ KV cache จะช่วยลด TTFT ได้มาก
layer 2Agency — ให้โมเดลไปหาข้อมูลเองได้
T4

Native Tool-Calling loop แทนการยัด prompt

2–3 วันเปลี่ยนเกม

นี่คือข้อที่เปลี่ยนพฤติกรรมมากที่สุด จาก "ตอบจากที่ให้ไป" เป็น "สอบสวนเอง" vLLM รองรับ OpenAI tool-calling อยู่แล้ว เปิดด้วย --enable-auto-tool-choice --tool-call-parser hermes (Qwen3 ใช้ hermes parser)

ชุด tool ที่เสนอ — อ่านอย่างเดียวทั้งหมด:

list_servers(filter?, health?)            // ทะเบียนเครื่อง + สุขภาพ
get_server_detail(server, window)          // Context Pack ของ T1 เฉพาะเครื่องนั้น
query_metrics(servers[], metric, window)   // เลือก raw/1m/1h อัตโนมัติตามช่วงเวลา
get_incidents(status?, server?, since?)    // incident ที่เปิดอยู่
get_incident_history(metric, server, days) // "เคยเกิดแบบนี้ไหม ครั้งก่อนแก้ยังไง"
get_ndb_topology(server?)                  // node / nodegroup / arbitrator / memory
get_services(server)                       // pm2 + docker + expected vs actual (drift)
get_alert_rules() / get_notification_stats(days)   // วิเคราะห์ alert fatigue
correlate(window, servers[])               // metric ที่ขยับพร้อมกันข้ามเครื่อง
run_sql(query)                             // ← ตัวเลือก ดูกล่องเตือนด้านล่าง
เรื่อง run_sql — ทรงพลังที่สุดและเสี่ยงที่สุด ถ้าจะเปิด ต้องครบทั้งชุด: DB role แยก monit_ai ที่ GRANT SELECT เฉพาะตาราง/วิวที่อนุญาต, SET LOCAL statement_timeout = '5s', บังคับ LIMIT, ปฏิเสธทุกอย่างที่ไม่ใช่ SELECT/WITH ด้วยการ parse ไม่ใช่ regex, บล็อก pg_read_file/dblink/COPY, และจำกัดสิทธิ์ให้ role admin เท่านั้น

loop จำกัด 5 รอบ มี token budget และ stream สถานะให้ผู้ใช้เห็นว่ากำลังทำอะไร ("กำลังดึงเมตริก 7 วันของ db-02…") ซึ่งทำให้การรอ 20 วินาทีรู้สึกต่างจากหน้าจอค้างมาก

เผื่อทางถอย — ถ้าไม่อยากรีสตาร์ท vLLM ตอนนี้ ทำ ReAct fallback ได้: ให้โมเดลตอบ JSON {"tool":…,"args":…} แล้ว parse เอง ได้ผลใกล้เคียงและไม่ผูกกับ flag ของ vLLM

T5

Intent Router + Context Budgeting

1 วันแก้ D6 ตรงจุด

แยกคำถามออกเป็นชนิดก่อนประกอบ context — lookup / analyze / report / topology / capacity ชั้นแรกใช้ keyword matching ราคาถูก ถ้ายังไม่ชัดค่อยยิง call สั้นมากไป vLLM ขอ JSON (guided_json, max_tokens: 64) ซึ่งใช้เวลาไม่ถึงวินาที

แล้วค่อยประกอบ context เฉพาะที่คำถามนั้นต้องใช้ ผลคือ prompt เล็กลง 5–10 เท่า คำตอบตรงขึ้น และ history ไม่ถูกดันออกจาก context window อีก

T6

MCP Server (monit-mcp)

1–2 วันผลทางอ้อม

เขียน tool layer เป็นโมดูลกลาง server/src/lib/ai-tools.js ครั้งเดียว แล้วเปิดสองทาง: (ก) agent loop ในแอป (ข) MCP endpoint แบบ stdio + streamable-HTTP

ได้อะไร: เปิด Claude Desktop หรือ Claude Code ต่อเข้ามาสอบสวน incident ได้ตรง ๆ ด้วยโมเดลที่ฉลาดกว่า ตอนเจอเคสยาก ทีมอื่นเอา tool ไปต่อยอดได้ และเข้ากับแนวที่คุณทำ moph-mcp-server ไว้แล้ว

ข้อควรระวัง — MCP ไม่ได้ทำให้โมเดล local ฉลาดขึ้นด้วยตัวมันเอง มันคือมาตรฐานการเชื่อมต่อ ตัวที่ทำให้ฉลาดขึ้นจริงคือ tool กับ context pack ใน T1/T4 อย่าลงทุน MCP ก่อนสองข้อนั้น
layer 3Memory & Output — ความจำองค์กร และผลลัพธ์ที่ใช้งานได้
T7

RAG สองชั้น — structured ก่อน vector

2–3 วันผลสูง ชั้น A

ชั้น A — Structured retrieval (ทำก่อน ไม่ต้องใช้ embedding เลย)

ดึง incident ในอดีตที่ metric + server ตรงกัน พร้อม notes, resolved_at และระยะเวลาที่ใช้แก้ → "เคสนี้เคยเกิด 3 ครั้ง ครั้งล่าสุด 12 ส.ค. ใช้เวลา 40 นาที บันทึกไว้ว่าแก้โดย…" แม่นกว่า vector สำหรับ metric signature และได้ผลตั้งแต่วันแรก

ชั้น B — Vector RAG บน runbook และเอกสาร

  • pgvector บน Postgres ที่มีอยู่แล้ว ไม่ต้องเพิ่ม infra ใหม่
  • embedding ที่รองรับไทยดี เช่น BGE-M3 — serve คู่กับ vLLM ตัวเดิมได้ (อีก process แบบ --task embed หรือใช้ Infinity/TEI)
  • index: docs/*.md ของโปรเจกต์เอง, DECISIONS.md, runbook ที่ทีมเขียน, postmortem
  • chunk 400–600 token overlap ~15% เก็บ heading path เป็น metadata
  • hybrid search สำคัญมาก — tsvector คู่กับ cosine แล้วรวมด้วย RRF เพราะข้อความไทยปนศัพท์เทคนิคอังกฤษ ทำให้ embedding อย่างเดียวมักพลาดชื่อเฉพาะอย่าง ndb.nodes_unhealthy

ชั้น C — Semantic cache (ทางเลือก)

คำถามซ้ำ ๆ อย่าง "server ไหนมีปัญหา" cache คำตอบสั้น ๆ 60 วินาที ลดโหลด GPU ตอนหลายคนเปิดหน้าพร้อมกัน

T8

Structured Output → HTML Report

2–3 วันตรงกับที่ขอ
อย่าให้ LLM เขียน HTML เอง — โมเดลขนาดนี้เขียน HTML ยาว ๆ แล้วพังบ่อย ช้า กิน token และเป็นช่องโหว่ XSS ที่สำคัญกว่านั้นคือ ตัวเลขในกราฟจะกลายเป็นสิ่งที่โมเดลจำมา ไม่ใช่สิ่งที่ฐานข้อมูลมีจริง

ทำเป็นสามขั้นแทน:

  1. server รวบรวมข้อมูลและคำนวณเอง (T1) → ได้ dataset จริง
  2. เรียก vLLM ด้วย guided JSON — vLLM ใช้ xgrammar บังคับ grammar ระดับ decoder จึงได้ JSON ตรง schema เสมอ ให้โมเดลผลิตเฉพาะ การตีความ

T9

Topology & Diagram Generation

1–2 วันข้อมูลพร้อมแล้ว

databases.ndb.nodes[] มีครบทั้ง id, type, host, status, nodegroup บวก arbitrator และ data/index memory — เพียงพอสำหรับวาดแผนผังจริง render เป็น SVG ฝั่ง server

  • จัดกลุ่มตาม node group ไม่ใช่เรียงตาม id — เพราะ node group คือหน่วยที่ตัดสินว่าคลัสเตอร์ตายหรือไม่
  • สีตาม status: STARTED / STARTING / MISSING
  • ไฮไลต์ node group ที่เหลือ node เดียว — จุดที่โหนดถัดไปตายแล้วคลัสเตอร์หยุดรับเขียน นี่คือสิ่งที่แผนผังต้องบอกและตารางบอกไม่ได้
  • แสดง MGM/arbitrator แยก พร้อมสถานะ arb_connected
  • แถบ data memory ต่อโหนด เพราะ NDB เต็มหน่วยความจำ = เขียนไม่ได้ = ล่มเหมือนกัน

แผนผัง dependency ทั่วไปก็สร้างได้จากข้อมูลที่มี: http checks บอกว่าเครื่องไหนเช็ค URL ของใคร, databases บอกว่าใครถือ connection, expected_services บอกว่าอะไรควรอยู่ตรงไหน

บทบาทของ LLM คืออธิบายแผนผัง ไม่ใช่วาดแผนผัง

T10

Eval Harness — วัดว่าฉลาดขึ้นจริง

1 วันทำก่อนเลย

ข้อที่คนข้ามบ่อยที่สุดและเสียใจทีหลังบ่อยที่สุด เพราะการปรับ prompt โดยไม่มีเครื่องวัด จะกลายเป็นการเดาว่า "รู้สึกว่าดีขึ้น" ซึ่งย้อนกลับไม่ได้เมื่อมันแย่ลง

  • ชุดคำถามทอง 30–40 ข้อ พร้อมคำตอบอ้างอิงที่ คำนวณจาก SQL — ground truth หาได้จริงเพราะเป็นตัวเลข
  • วัดสี่อย่าง: ความถูกต้องของตัวเลข, เลือก tool ถูกไหม, latency/token, และ hallucination rate (อ้างตัวเลขที่ไม่มีอยู่จริง)
  • รันก่อน–หลังทุกครั้งที่แก้ prompt เก็บเป็น server/test/ai-eval/ กับ script เดียว

เทคนิคเสริมที่ควรพิจารณาด้วย

  • Model routing — ถ้า VRAM เหลือ serve Qwen3-4B ควบไว้สำหรับ intent routing และคำถาม lookup (เร็วกว่าราว 10 เท่า) แล้วส่งเฉพาะงานวิเคราะห์หนักไปตัวใหญ่
  • Prefix caching ที่ vLLM — system prompt ที่ยาวแต่คงที่จะถูก cache KV ทำให้ TTFT ลดลงมาก และสำคัญขึ้นเมื่อ prompt โตตาม T1/T2
  • Chat logging + feedback — ตาราง ai_chat_log เก็บคำถาม, tool ที่เรียก, token, latency และปุ่ม 👍/👎 เป็นวัตถุดิบทั้งของ eval และของการ fine-tune ในอนาคต

07

สิ่งที่ต้องให้คุณตัดสินก่อนเริ่ม

Q1 รุ่นโมเดลที่ serve อยู่จริงคือรุ่นไหน

Qwen3-30B-A3B (MoE) กับ Qwen3-32B (dense) ใช้ tool-call parser และธง thinking ต่างกัน และ VRAM ที่เหลือก็ต่างกันมาก มีผลกับ T3, T4 และเรื่อง model routing

ขอผลลัพธ์ของ curl $VLLM_BASE_URL/models กับบรรทัดคำสั่งที่ใช้ start vLLM

Q2 รีสตาร์ท vLLM เพื่อเปิด tool-calling ได้ไหม

ถ้าเปิด --enable-auto-tool-choice --tool-call-parser hermes --enable-prefix-caching ได้ จะได้ทางที่นิ่งและเร็วกว่า ถ้าแตะ production ไม่ได้ตอนนี้ ผมทำ ReAct fallback ให้แทน

แนะนำ: เปิด เพราะได้ prefix caching ติดมาด้วย ซึ่งชดเชย prompt ที่จะยาวขึ้น

Q3 เปิด run_sql แบบอ่านอย่างเดียวให้ AI ไหม

เป็น tool ที่ทำให้ตอบคำถามที่เราคิดไม่ถึงล่วงหน้าได้ แต่ก็เป็นพื้นผิวโจมตีที่ใหญ่ที่สุดในข้อเสนอนี้

แนะนำ: เปิด แต่จำกัด role admin + DB role แยกที่ GRANT SELECT เฉพาะที่จำเป็น + statement_timeout + บังคับ LIMIT

Q4 ยอมเพิ่ม pgvector กับ embedding model ไหม

ต้องมี extension เพิ่มและ process embedding อีกตัว ซึ่งกิน VRAM ที่แชร์กับโมเดลหลัก

แนะนำ: ทำ structured retrieval (ชั้น A) ก่อนใน P4 แล้ววัดว่าคำถามแบบไหนยังตอบไม่ได้ ค่อยตัดสินใจเรื่อง pgvector จากข้อมูลจริง

Q5 report เก็บใน DB พร้อม permalink หรือดาวน์โหลดอย่างเดียว

เก็บใน DB ได้ประวัติ เทียบย้อนหลังได้ ส่งลิงก์เข้า Telegram ได้ แลกกับ migration เพิ่มหนึ่งไฟล์และเรื่องสิทธิ์การเข้าถึง

แนะนำ: เก็บใน DB — คุณมี RBAC กับ audit_log อยู่แล้ว ต่อยอดได้เลย

Q6 เริ่มที่เฟสไหน

ถ้าอยากเห็นผลเร็วที่สุด P1 อย่างเดียวก็เปลี่ยนคุณภาพคำตอบได้ชัดแล้ว ถ้าอยากได้ report เป็นเป้าหลัก ต้องผ่าน P1 → P3

แนะนำ: P0 + P1 รวดเดียว แล้วให้คุณลองใช้จริงก่อนตัดสินใจ P2 กับ P3
